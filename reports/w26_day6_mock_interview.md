## 一、模拟面试 Round 1 · 项目深挖（60min）

> 仿真纪律：限时 + 压力追问 + 被问倒必记话术库。面试官角色由 AI 扮演，回答为"参考稿"——它既是训练标准也是录屏脚本的延伸，实际面试时用口语化表达，不必逐字背。

### 1.1 开场自我介绍（3min，参考稿）

> 计时 2'52"，未超时；段末数字 R 开头，全部来自 acceptance_final。

"面试官好，我是 XXX。我用 26 周从零系统做了四轮 Agent 相关项目，最近完成、也是最有代表性的是 SCM Copilot——一个供应链智能运营平台，把知识问答、数据分析、业务审批三个能力整合到一个入口。

项目里最想讲的三件事：

第一，**平台化整合与无状态扩展**。之前是两个各自独立、SQLite 单实例的 Agent 应用，账号割裂、状态在内存里、没法水平扩展。我把它整合成模块化单体：MySQL 权威库、RBAC 统一账号、状态全外置。最终双实例 least_conn 无状态部署——**30 并发压测 210/210 全成功、P95 1.3 秒、5xx 为 0**，压测中间杀掉一个实例，210 个请求一个不掉，容器重启数据零丢失。

第二，**NL2SQL 数据分析**。让运营直接用自然语言查业务库。SQL 是模型生成的，直接执行有注入风险，我做了两层防御：sqlglot AST 四道闸校验 + 数据库只读账号兜底。**真实 100 条评测集执行准确率 0.97，20 条攻击用例 0 逃逸**，单次查询 P95 只有 39 毫秒。

第三，**调度与数据闭环**。上线后不能靠人盯：APScheduler 六个定时任务做知识库同步、日报、夜间评测。多实例**连续 30 个窗口 0 重复执行**，文档改完 5 分钟内向量库更新。

整个项目 **344 项测试全绿、ruff/mypy 零错误、故障演练五连不雪崩、真实 LLM 成本不到 20 块钱**。我的核心能力是完整闭环——从设计、实现、评测到部署、压测、故障演练，每一步都有可复现的验收证据。"

### 1.2 项目深挖 · Why 决策链（15min）

#### Q1. "先一句话说清楚：这个系统解决什么问题、给谁用？"

**参考稿（30s）**：
"给供应链运营和业务人员的一站式智能助手——同一入口问知识（RAG 查业务规则）、查数据（NL2SQL 拉报表）、办业务（Agent 调工具+高危操作人工审批）。解决的是'运营日常动作分散在多个系统、知识找不到、报表要等开发写 SQL'这三个效率问题。"

> 点评：结构 = 用户 + 三类能力 + 解决的三个问题。用"三个问题"对齐"三类能力"，面试官容易接话。

#### Q2（★重点练）"这些东西为什么不直接用 Dify / Coze？自己搭有什么必要？"

**参考稿（1min，三支柱 + 一句收束）**：

"我理解这个问题——企业要快速上线，Dify 这类平台是合理选择。但这里有三点：

1. **能力层级不同**。这个项目要的不是'拖个 workflow 跑通 demo'，而是 RAG 混合检索调优、NL2SQL 安全纵深、多实例零重复调度、故障演练降级链——这些是**平台能力**，不是平台功能。特别是 NL2SQL 的四道闸校验和 execution accuracy 评测方法学，Dify 是给不了、也改不出来的。
2. **安全边界要可控**。企业数据场景，'模型生成的 SQL 直接执行'这个边界必须自己定义：AST 校验层 + 只读账号权限层，纵深设计只能在自研代码里落地。
3. **成本**。平台按席位订阅，我这个项目 mock-first 开发，真实 LLM 全项目成本 ¥20 以内。

一句话：**不是要再造一个 Dify，而是要证明我能把 Dify 给不了的那层深度定制做出来**——这恰恰是这类岗位需要的工程能力。"

> 点评：标准"认可前提 → 三支柱 → 一句收束"结构。不贬低平台（显得客观），落点是"我的价值在深度定制"。

#### Q3. "讲讲 ip_hash 换 least_conn 的决策链——为什么换、前提是什么？"

**参考稿（1min）**：
"这是项目里我最想讲的一个决策。一开始双实例用的是 ip_hash 会话亲和，压测时发现流量严重不均——同一 IP 的长连接把请求全压在一个实例上。但我的判断是：**这不是路由配置问题，是状态管理问题**。ip_hash 存在的唯一理由是'实例内存里有状态'——checkpointer、审批单、会话、缓存、锁都在进程里，所以必须粘滞。

所以决策链是：先做**状态全外置核销**——checkpointer、审批、会话进 MySQL，幂等、缓存、锁进 Redis，身份用无状态 JWT，8 项清单逐项打勾；然后才把路由换成 least_conn。

结果是压测中杀掉一个实例，**210/210 请求不中断、5xx=0**，另一个实例自动接走全部流量，恢复后自动回来。反过来说：状态没外置完就换 least_conn 是危险的——这也是我面试里想主动讲的一个'翻车细节'。"

> 点评：S→问题→判断→决策链→R 数字，完整且带教训。追问"如果状态外置不完怎么办"→ 答"回退 ip_hash（ADR-04 回退条件）"，诚实不硬撑。

#### Q4. "项目里最难的两个技术问题是什么？"

**参考稿（1min，挑两个）**：

"排第一的是 **NL2SQL 评测方法学**。一开始我用 SQL 字符串比对判对错，结果发现同义 SQL——LEFT JOIN 和子查询、列序不同——结果完全一致但字符串不同，大量误判。后来改成**结果集规范化比对**：类型归一 + 排序键整行 + 列子集对齐，才真正测出'答对数据'。这个直接决定了 0.97 这个数字有没有意义。

第二是**多实例零重复调度**。不是'加把锁'就行，而是三层分治：调度器全实例跑保高可用、Redis leader 锁保互斥、任务幂等键兜底保最终一致。而且观测里出现过 2 个异常窗口，逐条查根因是测试残留实例持锁，不是生产行为——**'零重复'是在排掉异常之后才敢下结论的**。"

> 点评：选的两个问题分别命中"评测方法学"（反 Demo 化）和"分布式一致性"（高并发考点），且都带翻车细节——真实感是记忆点。

### 1.3 技术细节（20min · 四道闸 / 锁 / 迁移 / 缓存 / 未达项）

#### Q5. "sqlglot 四道闸具体怎么实现的？为什么不用正则？"

**参考稿（90s）**：

"四道闸按顺序过：

1. **单语句限制**：解析后只允许一个 root 节点，从源头防 `;` 堆叠注入；
2. **根节点类型白名单**：仅允许 SELECT / UNION 类——写操作在第一道就被挡；
3. **子句级遍历拦截**：DFS 遍历整棵 AST，任何节点命中 INSERT/UPDATE/DELETE/DROP/ALTER 即拒——防'SELECT 伪装嵌写'（比如 CTE 里藏 DELETE）；
4. **危险函数黑名单 + 强制 LIMIT**：sleep、load_file、INTO OUTFILE 等拖库/慢查询函数直接拒，所有查询强制加行数上限。

为什么不用正则：正则可以被注释（`--`、`/* */`）、编码、大小写、括号嵌套绕过，是**启发式**不是**解析**。AST 是确定性解析——把 SQL 变成语法树，子句级拦截没有逃逸路径。

只靠校验够不够？**不够**。所以加了纵深第二层：数据库侧 `nl2sql_ro` 只读账号——实测攻击语句在校验层漏掉也会被 MySQL 以 ERROR 1142 拒绝。校验层 + 权限层双保险。"

> 追问："校验被绕过会怎样？" → "被只读账号兜住，写不进（ERROR 1142 实测）；即使只读账号被同样提权（不可能，账号权限固定在 MySQL），还有 3s 超时 + 行数上限兜底。"

#### Q6. "多实例定时任务怎么防重？锁失效了怎么办？"

**参考稿（60s）**：
"三层分治，职责不重叠：

- **调度器全实例跑** → 高可用：任何一个实例挂了，其他实例的调度器继续触发，任务不丢；
- **Redis leader 锁互斥** → `SET lock:job:{name} {owner} NX EX 300`，抢到锁才执行；owner 校验防误释放，TTL 覆盖任务最长执行时间防死锁；
- **任务幂等键兜底** → 最终一致：日报用日期键、KB 同步用内容寻址，就算锁失效导致重复执行，副作用也只产生一次。

锁失效是最坏情况，靠第三层兜底。实测连续 **30 个窗口每个窗口只有 1 个实例 success**，job_runs 表逐窗口可查。"

#### Q7. "数据从 SQLite 迁 MySQL，怎么保证不丢不错？"

**参考稿（60s）**：
"三个手段：

1. **双校验**：行数一致 + 关键字段校验和比对（feedback 13 / audit 19 / checkpoints 358 断点 + 858 写入，迁移后全一致）；
2. **幂等脚本可重跑**：连跑 3 遍结果不变——中途失败可安全重试；
3. **功能级验证**：迁移后 HITL 断点续跑验证——老审批单能继续走完，证明数据不只'在'而且'可用'。"

#### Q8. "语义缓存命中了错误答案怎么办？"

**参考稿（45s）**：
"命中前**双闸门**：相似度阈值（≥0.92）+ 关键词校验（实体/数字必须命中），宁可漏缓存不命中错答案；命中答案带 TTL 防长期失效；用户反馈纠错会**主动失效**对应缓存键；最后夜间评测抽样看缓存命中率与正确率的偏离——偏离大说明阈值过松，收紧阈值。"

#### Q9（压力题）"你验收表里 40 并发 P95 是 2.08 秒，没达标。你怎么看？"

**参考稿（45s，态度 > 解释）**：
"如实讲：40 并发成功率是 100%、5xx=0，但 P95 2.08 秒超了 1.5 秒目标。根因有两个：ops 域 checkpointer（AsyncMySaver）单连接串行，ops_query 的 P95 到 3.4 秒；另一个是本机 Docker 共享 CPU/IO 的资源限制。所以我**正式口径取 30 并发**——P95 1.27 秒达标，这是我写在验收表里的口径。改进路线是连接池化或每请求独立连接，已进二期 backlog。

我的原则是：**数字不造假、未达标如实标注、每个未达标都有根因和路线**——面试里我觉得如实讲比硬撑可信得多。"

> 点评：这是"反 Demo 化"四原则的实战——面试官考的是态度（会不会藏指标）和判断力（能不能讲清口径），不是数字本身。

## 三、模拟面试 Round 2 · 系统设计（45min）

> 答题框架（面试通用，本项目就是活样例）：
> **30s 澄清 → 需求 → 容量估算 → 架构 → 数据模型 → 安全 → 演进**
> 白板表达纪律：边画边讲（mermaid 习惯），先说边界再动手。

### 3.1 题一 · "设计一个企业知识库问答系统"（25min）

**Step 0 · 澄清（30s，先开口）**：
"三个问题先确认：用户规模与并发？文档量与更新频率？是否需要答案溯源和权限隔离？"（假定：500 内部用户 / 峰值 50 QPS / 1 万文档日增 100 / 要引用溯源 / 按部门隔离）

**Step 1 · 容量估算**：
- 1 万文档 × 平均 300 chunk ≈ 300 万 chunk；向量维度 512（bge-small）→ 存储约 1.5GB，Qdrant 单容器足够
- 50 QPS 检索，混合检索 BM25+向量+重排，目标 P95 < 500ms（本项目实测 P95 27–300ms 级）

**Step 2 · 架构**（三层）：
```
用户 → nginx → 问答服务（FastAPI + SSE）
                ├─ 查询改写 / 语义路由
                ├─ 混合检索（BM25+jieba + Qdrant 向量 + RRF 融合 + 重排）
                ├─ LLM 生成（模型池多 provider 切换）
                └─ 引用溯源 + 反馈纠错 → 回流评测集
```

**Step 3 · 数据模型**：
`documents`（元数据/部门/权限）→ `chunks`（内容/向量 id/文档外键）→ `qa_feedback`（纠错回流）→ `eval_reports`（夜间评测趋势）

**Step 4 · 安全**：
RAG 输入消毒（含毒 chunk 丢弃）→ 检索层按部门过滤 payload → 输出 PII/密钥打码 → 全部审计

**Step 5 · 演进**：
语义缓存（双闸门）→ 夜间评测自动化 → 多租户字段隔离 → 数据量大后 Qdrant 分片（本项目实测 432 QPS/P95 27ms，千万级以下单容器够）

**点评**：直接用 SCM Copilot 的 kb 域降维讲，每一层都有真实数字支撑；面试官可顺势追问"缓存错答"→ 双闸门话术（Round1 Q8 复用）。

### 3.2 题二 · "设计一个带数据分析的客服系统"（20min）

**Step 0 · 澄清（30s）**：
"关键分歧：是'客服坐席在会话里查知识+查订单'，还是'运营用自然语言拉报表'？"（假定：两者都要——坐席会话辅助 + 运营问数）

**Step 1 · 容量**：
订单表万级~百万级；坐席并发低（50 座席），运营问数 QPS 更低但查询复杂（join/聚合）→ 关键指标是**查询延迟和正确率**，不是吞吐

**Step 2 · 架构**：
```
坐席/运营 → nginx → Agent 网关（RBAC + 审计 + 限流）
              ├─ 知识问答子图（同上）
              ├─ 数据查询子图：NL → Schema Linking → LLM → sqlglot 四道闸 → 只读沙箱 → 表格+SQL 透出 → 自修复 ≤2 次
              ├─ 业务操作子图：工具调用 + HITL 审批（高危写，before/after diff）
              └─ 调度域：夜间评测 / 语义缓存预热
```

**Step 3 · 安全（本题重点）**：
- NL2SQL 双保险：AST 四道闸 + 只读账号（ERROR 1142 兜底）
- **行级数据权限**：生成 SQL 时强制注入租户/坐席维度条件（防横向越权）
- 高危写操作 100% 审批 + 100% 审计

**Step 4 · 演进**：
错误自修复 → 多轮追问 → 语义缓存 → 报表订阅（调度日报）→ 数据量大后读写分离

**点评**：这题把 SCM Copilot 三域全部串起来，是"平台叙事"最完整的复现；强调行级权限注入是对面试官常见追问"NL2SQL 怎么防越权"的提前回应。
