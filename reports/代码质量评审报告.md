## 1. RAG 管线架构分析

**路径：** `F:\code\agent\learning-outputs\scm-copilot\backend\app\shared\rag\`

### 1.1 管线拓扑

```
PDF/Word/MD → chunks → Embedder(bge-small-zh) → SCMStore(Qdrant)
  → HybridRetriever(BM25+向量→RRF) → Reranker → SemanticCache → SemanticRouter
```

### 1.2 各组件实现程度

| 组件            | 文件                   | 实现程度             | 说明                                                         |
| --------------- | ---------------------- | -------------------- | ------------------------------------------------------------ |
| Parser          | `parser/pdf_parser.py` | **生产级**           | pdfplumber 抽文本+表格，字号检测标题，Markdown 输出          |
| Parser          | `parser/registry.py`   | **生产级**           | 路由 `.md/.pdf/.docx`，坏文件跳过并记录                      |
| Embedder        | `embedder.py`          | **真实实现**         | 使用 `SentenceTransformer`，`embed_query` 加 bge 检索指令，`embed_texts` 不加指令 |
| Store           | `store.py`             | **生产级**           | Qdrant Client，带 topic/tenant 过滤、批量 upsert、瞬时故障重试 |
| HybridRetriever | `hybrid_retriever.py`  | **生产级**           | BM25+向量双路召回，RRF/weighted 融合，Qdrant 故障时降级 BM25-only |
| BM25Index       | `hybrid_retriever.py`  | **生产级**           | jieba 分词，`rank_bm25.BM25Okapi`，支持缓存到 `bm25_index_cache.json` |
| Reranker        | `reranker.py`          | **真实+降级**        | `BGEReranker` 基于 `bge-reranker-base`，失败自动降级 `RuleReranker` |
| QueryRewriter   | `query_rewriter.py`    | **LLM依赖+mock降级** | rewrite/multi_query/hyde，mock 时返回原查询或单元素列表      |
| SemanticCache   | `semantic_cache.py`    | **生产级**           | Redis 权威 + 内存兜底，双闸门（embedding≥0.92 + Jaccard≥0.40），版本失效 |
| SemanticRouter  | `semantic_router.py`   | **生产级**           | 规则优先层 + kNN 样本投票 + bootstrap 原型兜底，data/tool/chat/rag 四分支 |

### 1.3 关键设计亮点

- **混合检索降级**：`hybrid_retriever.py` L193-214，Qdrant 异常时捕获并降级 BM25-only，带 `degraded=True` 标记
- **RRF 融合**：`hybrid_retriever.py` L131-145，`k=60`，不依赖分数归一化
- **语义缓存双闸门**：`semantic_cache.py` L44-62，防跨主题误命中
- **语义路由规则层**：`semantic_router.py` L52-70，高置信模式零 embedding 成本
- **缓存 TTL**：`semantic_cache.py` L36，Redis 语义缓存 TTL=7天

- 重排器测试不足：`backend\tests\test_hybrid_retriever_degrade.py` 覆盖检索降级，但没有看到对 `reranker.py` 独立重排路径的专项测试。

### 2.2 mock/real 切换机制

```python
n = (name or os.getenv("LLM_PROVIDER") or "mock").lower()
```

## 3. 可靠性组件

**路径：** `F:\code\agent\learning-outputs\scm-copilot\backend\app\shared\reliability\`

### 3.1 分布式锁

`distributed_lock.py`：

- 使用 `Redis SETNX + TTL + owner 校验`。
- `acquire()` 使用 `set_nx()`，`release()` 使用 `delete_if_equals()`：`distributed_lock.py` L41-62。
- Redis 不可用 → `fail-open` 返回 `True`，不加锁放行：`distributed_lock.py` L41-46。

结论：这是**真实分布式锁实现**，适合防并发写。

### 3.2 幂等

`idempotency.py`：

- Redis 后端使用 `SETNX + TTL`：`idempotency.py` L140-151。
- TTL 默认 300s：`idempotency.py` L35、L132。
- 只有 `SUCCESS` 才缓存结果，`RUNNING/FAILED` 不缓存：`idempotency.py` L5、L6、L165-175。
- 默认 `backend="auto"`，Redis 不可用 → `fail-open` 降级 sqlite：`idempotency.py` L193-221。

结论：Redis 幂等接近真实分布式幂等，但 Redis 不可用时的 sqlite 降级会退化为**单机幂等**。

### 3.3 熔断器

`circuit_breaker.py`：

- 三态状态机：CLOSED → OPEN → HALF_OPEN。
- `OPEN` 时快速失败，冷却后进入 HALF_OPEN 探测。
- `failure_threshold` 默认 5，`cooldown` 默认 10s：`circuit_breaker.py` L18-26。
- 调用包装器使用 `time.sleep()`：`circuit_breaker.py` L43-59。

结论：**单机进程内实现**，没有 Redis/分布式一致性。如果后端双实例部署，各自维护独立熔断状态。

### 3.4 重试策略

`retry_policy.py`：

- 单级重试：指数退避 + jitter：`retry_policy.py` L45-78。
- 可重试异常过滤：`is_retryable_http()`：`retry_policy.py` L26-40。
- 降级链：`degrade_chain()`，每级内部再套 `RetryPolicy`：`retry_policy.py` L83-139。

### 3.5 成本预算

`cost_budget.py`：

- 进程内 `threading.Lock` 保护：`cost_budget.py` L34。
- 会话预算表 `_budgets` 是进程内 dict：`cost_budget.py` L68-70。
- 多实例下预算不可共享：每个实例各自判断是否超预算。

### 3.6 Redis 客户端

`redis_client.py`：

- 模块级单例：`get_redis_client()`：`redis_client.py` L206-217。
- 健康检查缓存：失败后 5 秒内不反复探活：`redis_client.py` L29-30、L80-87。
- 所有操作 fail-open：异常返回 `None/False`：`redis_client.py` L89-203。

### 4.3 429 处理

SDK 错误模型支持 429 与 `Retry-After`：`errors.py` L54-59、L69-81。

但在当前 `ScmCopilot` 实现中，没有看到自动重试/退避逻辑：

- `_request()` 遇到 4xx 直接抛 `ScmError`：`__init__.py` L78-83。
- `chat_stream()` 在流开始失败时抛 `ScmError`：`__init__.py` L104-107。
- `nl2sql()` 通过 `_request()` 抛 `ScmError`：`__init__.py` L126。

也就是说：**SDK 能发现 429，但默认不自动重试**，需要调用方捕获 `ScmQuotaError` 后按 `retry_after` 退避。

### 4.4 SSE 解析

`chat.py`：

- 支持多行 `data:` 拼接：`chat.py` L24-26、L43-44。
- 空行分隔事件：`chat.py` L40-42。
- JSON 解析失败跳过，不中断流：`chat.py` L36-38。
- 兼容 `event:` 命名行：`chat.py` L45-47。

### 4.5 问题

- SDK 缺少自动重试/429 退避。
- 文档中没有显式说明 SDK 默认不重试，可能导致集成方误判。
- `chat_stream()` 仅返回 `Iterator[ChatEvent]`，没有返回事件类型列表或异常事件结构。

## 总结

该项目 RAG 管线设计较完整，核心链路是：PDF/Word/MD 解析 → chunks → bge embedding → Qdrant 向量存储 → BM25+向量 RRF 混合检索 → reranker → semantic cache → semantic router。LLM provider 抽象清晰，mock/real 切换依赖 `LLM_PROVIDER` 环境变量，mock 侧具备上下文感知、冲突检测和成本估算。可靠性组件中，分布式锁和 Redis 幂等是较接近真实分布式实现，但熔断器和成本预算是单机实现，语义缓存也没有独立的 TTL 淘汰策略。SDK 错误模型较完整，但默认没有自动重试/429 退避。部署栈较完整，包含双实例后端、nginx、Prometheus、Grafana 和 chaos 演练脚本。主要改进点集中在 `real_provider.py` 拆分、reranker/real_provider 测试补充、SDK 429 自动重试设计、fail-open 场景风险说明，以及 frontend 空壳的明确定位。
