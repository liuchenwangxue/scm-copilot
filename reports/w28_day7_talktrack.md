## 线一 · 性能修复线（W27 叙事，"发现→定位→池化→前后数字"3 分钟版）

**开场**：
"一期验收 18 项里唯一没达标的硬指标是 40 并发 P95=2087ms（目标 ≤1.5s）。我把它当成二期第一优先，最后打到了正式口径达标。"

**三段**：
- **问题**：40 并发 P95 2087ms 超时；根因排查发现 ops 域 LangGraph 的 checkpointer 持单 asyncmy 连接串行执行——20 路并发耗时 ≈ 20×单路。
- **动作**：① Checkpoint 连接池化（组合包装 130 行，`pool.acquire()` 每操作临时 Saver 委托，未 fork 第三方类——评审提的 fork-vs-postgres 决策点就此关闭）；② 40 并发净环境复验（停 21 个非本项目容器只留 scm 栈）；③ 唯一代码优化：LangGraph `durability="exit"` 合并写（一次图执行 checkpoint 写放大 20 行→1 行）。
- **数字**：30 并发 P95 **1269→714ms（-44%）**（正式 Gate）；20 并发 -65%；40 并发 2087→1872~2095ms 如实记录并归因（本机 12 核 VM 吞吐天花板）；成功率 100%、5xx=0。

**翻车细节**："40 并发最终没压进 1.5s——我没有硬凑，而是用净环境复验证明了是机器吞吐天花板而非代码瓶颈，并主动把正式口径修订为 30 并发（稳达）。归因链完整比数字好看更重要。"

**追问：池大小怎么定？** "Little's law：并发数 × 平均持有时长 / 1s ≈ 需求连接数。40 并发 × 50ms ≈ 2 条忙连接，池 10 是余量——所以是 10 不是 40。"

## 线二 · 规模化演进线（ADR-009/010/011，三层递进）

**开场**：
"二期我把三个'规模化有路'的决策写成 ADR 并落地了开关/PoC——租户分片、读写分离、自研 Runtime 边界。"

**三段**：
- **租户隔离三级演进（ADR-009）**：payload 过滤（零迁移，单 collection）→ **collection 分片**（crc32 路由 4 分片 + BM25 租户过滤补丁，双保险）→ 独立实例。触发条件量化：租户数 > 12 或单 collection > 10 万点。**数字**：2386 点 12 租户铺满 4 分片；BM25 双租户零交集。
- **读写分离（ADR-010）**：L1 单主 → L2 读写分离（DbRouter 开关，读走 RO DSN，无副本零行为差异）→ L3 拆库。**数字**：RO 路由 6 用例绿，本机零行为差异实证。
- **框架退出路径（ADR-011）**：自研 Runtime 内核 PoC（~120 行，图节点循环 + 原生 tool-calling 循环双形态），data 图同构对照。**数字**：18 用例绿，LangGraph 同输入同输出。

**翻车细节**："crc32 对少量租户会倾斜——不是修 bug 而是接受并记录（分片数 > 租户数时空分片零成本），演示数据补足 12 租户验证铺满。工程取舍比完美主义值钱。"

**追问：为什么不全上分片/不迁全部图？** "分片是性能隔离，payload filter 是正确性兜底，双保险保留；Runtime 只迁 data 域——ops 的 interrupt/checkpointer 生态是 LangGraph 主场，PoC 边界就是 ADR 论点。"

## 线三 · 学习资产回归线（新增，D 类四项回归）

**开场**：
"我 6 个月按周迭代学习，二期专门做了'学习资产回归'——把前期学过的能力合并进平台，不是从零造。"

**三段**：
- **MCP 双侧**："W6 我做过生产级 FastMCP server（7 工具 + RBAC + 审计 + 重试 + 幂等，双传输），W21 做过 MCP client 消费第三方工具。二期把两半资产合并——FastMCP 包装平台 ops registry，暴露三只读工具，@mcp.tool→@audit_call→@require_permission 三层栈，鉴权复用平台 API Key。**数字**：kb 域自己的 MCPClient 调通平台 MCP server（dogfooding 闭环），6 用例；高危写工具不暴露。**坑**：MCP stdio 的 stdout 是 JSON-RPC 协议通道，审计日志 print 到 stdout 会污染协议——加 echo=False 修复。"
- **原生 tool-calling 双路径**："平台既有'结构化 JSON 选工具'（mock-first），二期 Runtime PoC 内核支持原生协议形态（tools schema→tool_calls→registry 执行→回填→终答）——这是 w11/w12 SDK 经验回归。**trade-off**：原生是 Provider 标准协议、多轮循环成熟；结构化是 schema 自控、mock 友好、Provider 无关。"
- **记忆分层（ADR-012）**："现状四件套：工作记忆=MySQL checkpoint、短期=Redis session_ctx、会话元数据=conversations、长期记忆原材料=feedback 表（W23 建表至今未回流）。设计回流管道：夜间 job 挖掘 correction → user_preferences 表 → prompt 注入。**为什么代码留三期**：记忆回流是锦上添花，优先级低于 MCP/性能/覆盖率——主动排期体现工程取舍。"

**追问：接入方式为什么是全家桶？** "SDK（程序化调用）、OpenAPI（标准 REST）、webhook（出站通知）、MCP（AI 客户端入站）——四个接入面服务四种消费者，每层都有实测证据。"

## 线四 · 多 Agent 判断线（新增，w13 OW 引用）

**开场**：
"关于多 Agent，我不只是'评估过不需要'——我**做过生产级 Orchestrator-Worker**，然后才判断 scm 单图更优。"

**三段**：
- **做过**："W13 我用 LangGraph 实现过生产级 OW 编排：Send API 并行分发子任务、planner/validator 回退、LangFuse span 树观测——是实物不是概念。"
- **评估过**："scm 三域（kb/ops/data）分解干净、单域内是线性的 7 节点 DAG，没有需要动态拆解的子任务——单图 + 条件边足够，多 Agent 反而引入编排开销与调试黑盒。"
- **知道何时上**："触发条件明确：问题需要复杂拆解（多文档交叉、多步工具链）、子任务可并行、需要独立失败回退。三期已排 data 域 planner-worker PoC（w13 架构回归）。"

**翻车细节**："我一开始也想'上多 Agent 显得高级'，但压测和调试成本告诉我：没有拆解需求时，单图 + 明确的条件边是最优解。'做过、评估过、知道何时上'三层递进才是完整答案。"

## 高频追问弹药（补充）

| 追问 | 答案要点 |
|---|---|
| 为什么不直接用 Dify/Coze？ | harness 自研 + 定制安全闸（四道闸）+ 成本控制（mock-first ¥20） |
| 数据量涨 100 倍哪里先崩？ | 单库写入（ADR-010 L3 拆库信号）→ Qdrant 分片（ADR-009 已落 L2） |
| 框架抽象的税是什么？ | 隐式行为黑盒（approval_gate resume 重跑实测踩坑）、版本迁移风险、能力被框架上限锁死 |
| 原生 tool-calling vs 结构化 JSON？ | 原生=Provider 标准协议/流式参数/多轮循环；结构化=mock 友好/Provider 无关——mock-first 现实选择 |
| 记忆为什么四件套不统一？ | 写频+TTL→Redis；审计追溯→MySQL；JWT 只放身份不放会话——按数据属性选载体 |
| 40 并发没到 1.5s？ | 净环境复验归因机器天花板，正式口径 30 并发 714ms 稳达，如实记录 |
