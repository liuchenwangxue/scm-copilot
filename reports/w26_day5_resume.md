## 三、STAR 三主线脱稿训练（每条 ≤3min，录音自查）

### 主线 1 · 平台化整合（"从两个单实例到杀不死的生产平台"）

**S/T**：两个独立 Agent 应用（知识问答/业务操作）各自 SQLite 单实例、账号割裂、状态在进程内存里，无法水平扩展——"上线容易运营难"；任务是把它们整合成一个统一账号/审计/调度/监控、双实例无状态的生产平台。

**A**：
1. MySQL 8 权威库 + Alembic 版本化（12 表从零可重放）+ RBAC 三级权限 + JWT 双令牌统一身份；
2. 状态全外置核销：checkpointer/审批/会话 → MySQL，幂等/缓存/锁 → Redis（8 项清单逐项打勾）；
3. 路由从 ip_hash 换 least_conn——前提就是状态外置完成；
4. 双实例 + 压测 + 杀实例演练验证。

**R**（数字开头）：
> **109 项**旧回归折算 68 项全绿、40 并发成功率 100%（正式基线 30 并发 P95 1.3s）、压测中杀一个实例 210/210 请求不中断 5xx=0、容器重启数据零丢失、4 类迁移数据校验和全一致。

**翻车细节（真实感）**：ip_hash 粘滞路由导致同一 IP 长连接把流量全压在一个实例上——教训是**路由策略不是配置问题，是状态管理问题**；状态外置没做完之前 least_conn 是危险的。

### 主线 2 · NL2SQL 安全与准确（"敢让模型直接写 SQL"）

**S/T**：平台要用自然语言查业务库——既要查得准（生成 SQL 语义正确），又要防注入/越权/拖库，而 LLM 生成的 SQL 天生不可全信；任务是从零建 NL2SQL 数据分析域并保证安全。

**A**：
1. sqlglot AST 四道闸（单语句/仅 SELECT/子句级禁写/危险函数黑名单）+ 强制 LIMIT；
2. 数据库层 `nl2sql_ro` 只读账号兜底（纵深防御——校验有未知绕过权限层也写不进）；
3. Schema Linking 表列召回 + few-shot + 错误自修复 ≤2 次（修复后强制重过四道闸）；
4. execution accuracy 评测（结果集比对，非字符串比对）。

**R**（数字开头）：
> **0.97** 整体执行准确率（real 100 条，单表 0.98 / join 0.95 / 聚合 1.0）、**20/20** 攻击用例 0 逃逸、real P95 39ms、自修复救回 0.93、Schema Linking token 降 53% 精度反升、SQL 100% 透出可审计。

**翻车细节（真实感）**：最开始想用 SQL 字符串比对评测——发现同义 SQL（LEFT JOIN vs 子查询）大量误判，改**结果集规范化比对**才真正测出"答对数据"。

### 主线 3 · 数据闭环自动化（"上线后不用人盯"）

**S/T**：知识库新鲜度、质量回归、审计归档、经营日报全靠手动，"上线后怎么维护"没有答案；任务是用调度把数据闭环自动化，且双实例**不能重复执行**。

**A**：
1. APScheduler + MySQL job store（任务定义重启不丢）+ Redis leader 锁；
2. 六任务（KB 同步 /5min、向量清理、审计归档、日报 /1-5 08:00、夜间评测 /2:00、缓存预热 /7:00）；
3. 三层防重分治：全实例跑保高可用 → 锁保互斥 → 幂等键保最终一致；
4. 每次执行落 job_runs（status/instance/duration_ms）——零重复有证据、失败有现场。

**R**（数字开头）：
> **30/30** 稳态窗口零重复（逐窗口 job_runs 证据）、KB 增量同步 ≤5min、日报 GMV 3674 万/延迟率 9.9% 数字可回溯 SQL、夜间回归质量劣化次日可见、月真实成本 ≈¥20。

**翻车细节（真实感）**：观测中出现 2 个异常窗口（06:00 双 skipped / 06:15 双 success）——逐条查根因发现是测试残留实例持锁 + 部署重建窗口，非生产行为；**"零重复"是在排掉异常后才敢下结论的**。

## 五、追问弹药补充（W26 手册 Day5 下午 5）

### 5.1 数据量涨 100 倍哪里先崩？（ADR-01 拆分信号③ + ADR-03 演进路径）

> 口述顺序：**单库写瓶颈 → 向量库容量 → 检索/生成资源**，每个都有演进路径，不硬撑。

1. **第一崩：MySQL 单库写入**——checkpointer/审批/会话/业务数据全在主库，写入集中是模块化单体的已知上限（ADR-01 拆分信号③"单库写瓶颈"）。100 倍 → 按域拆分：data/ops 独立库或读写分离。
2. **第二崩：Qdrant 单容器向量库**——当前千万级以下 432 QPS/P95 27ms 足够；100 倍数据量超单容器能力 → ADR-03 演进路径：先分片（多 collection/分片），仍不够评估 Milvus 集群。
3. **第三崩：NL2SQL/LLM 生成吞吐**——生成链路是计算密集，100 倍 QPS 时 LLM 吞吐先到顶；应对：mock-first 成本可控 + 模型池横向切换 + 计算密集域独立扩缩容（=拆分信号①）。

### 5.2 为什么不用向量库存日志？（选型按查询特征）

> 一句话：**日志是 append-only 时间序列 + 精确/模式检索，不是语义相似度查询——用向量库存日志是杀鸡用牛刀。**

1. 日志查询特征：时间范围过滤 + 关键字/正则 grep（如按 request_id/trace_id 精确查）——**文本精确匹配**不是向量语义；
2. 向量库索引写入成本高（embedding + HNSW 构建），日志写入是高频路径，指数级放大成本；
3. 本项目做法：结构化 JSON 日志（每请求一条，X-Request-Id⇔trace_id 贯穿）+ 审计表落库——取证用 SQL 查，趋势用 Prometheus 指标，单链路用 LangFuse；日志量再大走 Loki/ELK（按标签+时间）。

### 5.3 多租户怎么扩展？（tenant_id 贯穿 + 演进路径）

> 当前：**字段级租户隔离**——Qdrant payload 租户过滤、MySQL 所有表 tenant_id、RBAC 三级权限（3 租户 × 4 角色）、JWT claims 带 tenant_id 权限零查库。

1. 数据隔离：检索层 payload 过滤 + SQL 层强制 WHERE tenant_id（NL2SQL 生成时注入租户条件，防越权）；
2. 认证隔离：JWT claims 带 tenant_id + roles，RBAC 矩阵 12 组 allow/deny 全过；
3. 演进路径（租户量增长时）：租户少（<100）字段过滤够用；租户多 → 按租户哈希分片（Qdrant）/ 分库分表（MySQL，复用 ADR-01 拆分信号③）；**先看真实租户负载特征再拆，不为"多租户"设计过度架构**。
