### Day1（8/31 周一）★ 容器口径统一（C1）

**目标**：容器内跑真模型，评测/压测/演示三口径合一。

**上午**：
1. 模型进容器（首选卷挂载，避免镜像膨胀）：
   ```yaml
   # docker-compose.yml backend-a1/a2 加：
   volumes:
     - model-cache:/root/.cache          # 本机下载好的 bge 模型挂进去
   environment:
     - SCM_EMBEDDER=real
     - SCM_RERANKER=real
     - SCM_SEMANTIC_CACHE=on             # 容器内语义缓存开启
   ```
2. 启动健壮性：模型加载失败（卷未挂/下载不全）→ 自动回退 mock embedder/RuleReranker + 启动日志大写 WARNING + `/health` 里暴露 `embedder=degraded`（降级哲学贯穿）
3. reranker 体积权衡：1.1GB 挂载只给 backend 一台（a2 保持 RuleReranker），`/health` 可见两实例差异——本身就是"分级降级"的演示素材

**下午**：
4. 口径对齐实测：容器内跑 `eval_nightly`（RAG 156 条）与本机分数对比——目标分差 ≤2pp（hit@1 本机 0.9038，容器 ≥0.88）
5. 容器内压测快跑（30 并发）确认 P95 不因模型劣化超 W27 基线 ×1.3
6. 把"容器内外评测对照表"落 `reports/w28_report.md` 第一节

**面试题 0.5h**：镜像体积 vs 运行时下载模型的取舍？（学习项目卷挂载零成本；生产镜像内嵌保证不可变部署；中国网络环境 HF 镜像源 `HF_ENDPOINT=https://hf-mirror.com`——细节即真实感）

**验收**：容器内 eval 分差 ≤2pp；两实例 health 可见模型状态；语义缓存容器内命中。
**坑**：
- `sentence-transformers` 首次 import 会联网查版本——设 `SENTENCE_TRANSFORMERS_OFFLINE=1` 或 `HF_HUB_OFFLINE=1`
- Windows Docker Desktop 卷挂载大模型目录 IO 慢——用 named volume 不是 bind mount
- 本周起所有验证都在容器内做，本机结果只做对照

**上午**：

   ```python
   from scm_client import ScmCopilot

       for ev in client.chat_stream(message):        # SDK 0.2.0，遇 429 自己退避

               case "message": yield ev.text
               case "data_table": ...                # 转 DataFrame 附件

   ```
2. 对话页：SSE 流式打字、`data_table` 渲染 `gr.Dataframe`、SQL 放 `gr.Accordion("查看 SQL", open=False)` 折叠、引用溯源列表

**下午**：
3. 审批页：`approvals.list_pending()` 表格 + 行内通过/驳回按钮（`gr.Button` 每行事件）→ `approvals.decide()`

**面试题 0.5h**：为什么 Gradio 不是 React？（演示 ROI：一天 vs 一周；面试考察点在 SSE/协议设计不在 CSS；"前端正式化"列入三期——技术选型的机会成本意识）

### Day4（9/3 周四）★ 多租户分片（C4/C5/B7 项）

**目标**：租户隔离从"payload 过滤"演进到"分片路由"，BM25 路隔离漏洞排查补齐。

**上午**：
1. 先堵 C5：排查 BM25 路租户过滤——`BM25Index` 的 chunk 元数据若无 tenant 维度则补：构建时 chunk 带 `tenant_id`，检索时先按租户过滤再打分（两租户语料交集实验证）
2. 分片路由（`shared/rag/sharding.py`）：
   ```python
   def collection_for(tenant_id: str, shards: int = 4) -> str:
       return f"kb_{zlib.crc32(tenant_id.encode()) % shards}"
   ```
   TenantFilter 改造：`retrieve()` 先路由 collection 再注入 payload filter（双保险保留——分片是性能隔离，filter 是正确性兜底）
3. ADR-009：记录"payload filter → collection 分片 → 独立实例"三级演进及触发条件（租户数 > X 或单 collection 点数 > Y）

**下午**：
4. 迁移脚本：现有单 collection 按租户哈希搬入 4 分片（uuid5 保持 point id，幂等可重跑）
5. 验证三件：`verify_isolation()` 分片模式下过；两租户并发检索性能对比（隔离语料更小 → 更快）；单分片删除文档不影响其他分片
6. 回归：KB 域全量测试绿（TenantFilter 接口不变，内部路由对调用方透明）

**面试题 0.5h**：租户隔离的三种层级及成本（payload filter 查询慢但零迁移；分片查询快但要路由层；独立实例最贵最干净——什么时候升一级：看 P95 与点数增长曲线）

**验收**：4 分片就位；BM25 双租户语料零交集；verify_isolation 绿；KB 回归绿。
**坑**：
- crc32 分布不均：4 分片 × 少量租户会倾斜——演示数据补足 12 租户验证分布（或直接说明并接受倾斜）
- 迁移期间新旧 collection 并存：开关 `SCM_SHARDING=on/off` 灰度，回退零成本
- Qdrant 分片 collection 的 HNSW 参数要一致（否则分片间召回率不齐）

### Day5（9/4 周五）★ MCP Server 资产回归 + IM webhook 最小版 + 读写分离 ADR（D1/C6/C7，B6/B8 项）

**目标**：开放生态闭环（SDK→OpenAPI→webhook 出站→MCP server 入站）；审批出平台最小版；拆库路径成文。

**上午（MCP Server 资产回归，前期 w6 实物回归）**：
1. **背景**：W6 已做过供应链 FastMCP server（7 工具+RBAC+审计+重试+幂等），其工具清单与 ops registry 同域同名（query_order/update_order）；kb 域有 MCP client（W21）——本日把"两半资产"合并：**FastMCP 包装 ops tool registry，平台正式具备 MCP server 侧**
2. 实现（复用面极大）：
   - `ops/notify/../mcp_server.py` 或独立 `backend/mcp_server/main.py`：`FastMCP("scm-ops")` 注册 `query_order` / `query_inventory` / `daily_report`（**只读工具优先**）
   - 权限/审计装饰器直接抄 w6 模式（`@mcp.tool() → @audit_call → @require_permission` 三层栈）；鉴权复用平台 API Key（`X-Api-Key` 头 → 现有 rbac 校验）
   - 高危工具（update_order/cancel_order）**不暴露**或映射到审批流——MCP 调用方触发高危 = 走 approval_gate（写清边界注释）
   - compose 加 mcp-server 服务（stdio 包 HTTP transport，复用 w6 的 client_http_test.py 模式测试）
3. **dogfooding 闭环测试**：kb 域自己的 MCP client（W21）连平台自己的 MCP server，跨域调一次 query_order——"自产自销"是面试最漂亮的演示素材
4. 面试叙事就绪："我 MCP 双侧都做过：W6 生产级 server（RBAC/审计/重试/幂等），W21 client 消费第三方工具，本日合并进平台——接入方式全家桶（SDK/OpenAPI/webhook/MCP）"

**下午**：
5. 审批 IM 推送最小版（半小时版，挂 `approval_requested` 钩子）：企微/钉钉群机器人 webhook POST 摘要卡片（审批 id+工具+字段名，**不发敏感值**）；3s 超时+1 次重试后放弃（通知尽力而为，审批状态机不受影响）；`SCM_WEBHOOK_URL` 空=关闭；无真群用本地 echo 服务模拟
6. ADR-010 读写分离（B8，只写文档+开关不动数据）：
   - 现状：平台库/业务库已分（alembic vs alembic_biz 双库）；读写未分
   - 方案：`session_factory` 拆 read/write 两个 DSN（`SCM_DB_RO_DSN`），NL2SQL executor 与报表查询走 RO；本机无副本 → DSN 相同时零行为差异
   - 实施 `shared/db.py` 路由开关（20 行，测试用两个 DSN 断言路由正确）
7. 回归 + 半周检查（Gate 前四项勾）

**面试题 0.5h**：MCP 与直接 REST API 暴露工具的区别？（标准化工具发现/Schema 协商/多传输/生态复用——Claude/Cursor 等客户端零成本接入；代价是多一层协议开销——什么时候值得）

**验收**：MCP server 三只读工具可被 kb client 调通（dogfooding 证据）；webhook 群内收到审批卡片实测（或 echo 模拟）；RO 路由单测绿；ADR-010 入库。
**坑**：
- FastMCP 的 Context 注入与平台 API Key 鉴权叠加——w6 的 `get_identity(ctx)` 模式直接抄，别重新发明

### Day6（9/5 周六）★ Runtime PoC（原生 tool-calling 内核）+ 记忆 ADR-012 + 终验（C8/C9/D2/D3，B4 收尾）

**目标**：自研 agent loop 最小内核跑通 data 图（B5 PoC 口径，内核用原生 tool-calling 协议形态——w11/w12 经验回归），记忆分层 ADR 成文，覆盖率冲 75%，混沌复验。

**上午**：
1. `shared/runtime/loop.py` 最小内核（~100 行，data 域同构，**tool-calling 循环为内核**）：
   ```python
   # 内核双形态：图节点循环（data 域用）+ 原生 tool-calling 循环（w11/w12 路径回归）
   async def run_tool_loop(llm, tools: list[ToolSchema], registry, state, max_steps=10):
       for step in range(max_steps):
           resp = await llm(messages=state["messages"], tools=[t.schema for t in tools])
           if not resp.tool_calls: return resp.text          # 终答
           for tc in resp.tool_calls:                        # 原生协议形态：tool_calls → 执行 → 回填
               result = await registry[tc.name].ainvoke(tc.args, ctx)
               state["messages"].append(tool_result(tc.id, result))
       raise ToolLoopError(f"exceeded {max_steps}")
   ```
   - data 图 7 节点 + 3 路由函数以图形态搬上去（generate/validate/execute/repair/reject/format/degrade），mock 全链路跑通且结果与 LangGraph 版一致（同输入同输出对照测试）
   - **原生 tool-calling 形态**（D2 回归）：loop 内核支持 `tools schema → tool_calls → registry 执行 → 回填 → 终答` 的标准循环——这正是 w11 day2_tool_demo / w12 的路径；与平台现有"结构化 JSON 选工具"形成双路径对照（面试讲清两者 trade-off：原生协议是 Provider 标准能力、结构化输出是 mock-first 的选择）
   - ADR-011：记录"何时值得自研"（框架税：checkpointer/interrupt 生态绑定 vs 内核 100 行可控；结论=PoC 保留、kb/ops 留 LangGraph、混合运行）
2. **ADR-012 记忆分层设计（D3 回归，半小时，代码留三期）**：画出现状四件套流向图——工作记忆=MySQL checkpoint（ops 域消息+HITL 现场）、短期=Redis session_ctx（data 域轮次，W27-D2 外置）、会话元数据=conversations 表（MySQL）、**长期记忆原材料=feedback 表（W23 建表至今未回流）**；设计回流管道：夜间 job 挖掘 feedback.correction + 查询历史 → 用户偏好表（MySQL）→ 注入 kb/data prompt（三期第一项）——"数据已在积累，管道三期接通"即面试完整答案

**下午**：
