## 2. 自测八题（面试前过一遍，先遮答案）

### Q1 · 为什么用模块化单体而不是微服务？什么信号出现时你会拆？

域间强关联（知识问答要引用业务数据语义）、单机资源约束、无多团队并行开发需求——拆分只增加运维复杂度不增加价值。模块已按 API 边界隔离，出现以下信号再拆：①某域负载特征显著不同（如 NL2SQL 计算密集需独立扩缩容）②团队分工需要独立发布节奏 ③单库写入成为瓶颈。

### Q2 · ip_hash 换 least_conn 的前提是什么？

所有会话相关状态外置——LangGraph checkpointer 进 MySQL、审批单进 MySQL、幂等/缓存/锁进 Redis、身份用无状态 JWT。粘滞路由存在的唯一理由是"实例内存里有状态"；状态外置后 ip_hash 反而造成负载不均（同一 IP 长连接压死一个实例）。

### Q3 · sqlglot 四道闸分别防什么？只靠它够吗？

①单语句限制防 `;` 堆叠注入 ②根节点仅 SELECT/UNION 防写操作 ③子句级遍历拦截 INSERT/UPDATE/DELETE/DROP 等防"SELECT 伪装嵌写" ④危险函数黑名单防 sleep 拖库/读文件。**不够**——校验层可能有未知绕过，所以再配数据库层 nl2sql_ro 只读账号 + 3s 超时 + 行数上限，纵深防御，即使校验有漏权限层兜底。

### Q4 · NL2SQL 评测为什么用 execution accuracy 而非 SQL 字符串比对？

同义 SQL（LEFT JOIN vs 子查询、列序不同、别名不同）结果一致但字符串不同，字符串比对会大量误判为错；评测目标是"答对数据"不是"写出一模一样的 SQL"。实现上对结果集做规范化（排序键 + 类型归一）后比对。

### Q5 · APScheduler 多实例如何防重复执行？

调度器全实例运行（高可用，实例挂了别人接管），任务触发时抢 Redis 锁 `SET lock:job:{name} {owner} NX EX 300`，未抢到的跳过本轮；owner 校验防误释放，TTL 覆盖任务最长执行时间防死锁；再配任务幂等键（如日报用日期作键）双保险——即使锁失效重复执行也只产生一次副作用。

### Q6 · 语义缓存命中了错误答案怎么办？

双闸门：相似度阈值（如 ≥0.92）+ 关键词校验（实体/数字必须命中）才可命中；命中答案带 TTL；用户纠错反馈触发对应缓存键失效；夜间评测抽样检查缓存命中率与正确率的偏离，偏离大说明阈值过松需收紧。

### Q7 · 模型池自动切换的触发条件？如何防重复计费？

触发：额度耗尽（401/429 配额类）、超时、5xx。切换在 provider 层内完成，对上层透明；写操作带幂等键（请求指纹），切换重试时服务端幂等去重，不会重复执行/重复计费；usage 按模型分别记账，成本报表可追溯。

### Q8 · 为什么保留 Qdrant 不用 Milvus？

W5 实测：千万级以下数据 Qdrant 432 QPS / P95 27ms 完全够用；单容器运维成本远低于 Milvus 集群（etcd+多角色）；HNSW 参数可调做过实验（还发现 full_scan_threshold 默认值使小数据 HNSW 静默失效的坑）。选型原则：场景与运维成本优先，不是越流行越好；数据量或分布式需求变化时再评估迁移。

### 放弃项话术（scope 质疑的统一回应）

"这些不是不会，是按生产价值筛选后明确不做——单机 Agent 服务场景下 ROI 不划算，我把时间花在 NL2SQL/调度/开放 API 这类无论做什么项目都要有的基础设施上。"

### Dify/Coze 三支柱话术（W26 Day6 重点练，Round1 实战过关）

> 结构：认可前提 → 三支柱 → 一句收束。不贬低平台（显得客观），落点是"我的价值在深度定制"。

1. **能力层级不同**：项目要的不是"拖 workflow 跑通 demo"，而是 RAG 混合检索调优、NL2SQL 安全纵深、多实例零重复调度、故障演练降级链——这些是**平台能力**不是平台功能，尤其 sqlglot 四道闸和 execution accuracy 评测方法学是 Dify 给不了也改不出来的。
2. **安全边界要可控**：企业数据场景，"模型生成的 SQL 直接执行"的边界必须自己定义——AST 校验层 + 只读账号权限层的纵深设计只能在自研代码里落地。
3. **成本**：平台按席位订阅；本项目 mock-first，真实 LLM 全项目成本 ¥20 以内。

> **一句收束**："不是要再造一个 Dify，而是要证明我能把 Dify 给不了的那层深度定制做出来——这正是这类岗位要的工程能力。"
> 追问"自研人力成本不算吗？"：**"单机 Agent 场景下自研的运维与学习成本是固定投入，订阅费是每月持续成本；且这个项目本质是能力沉淀，不是交付物。"**

## 7. 系统设计答题框架（Round2，W26 Day6 沉淀）

> 六步框架：**30s 澄清 → 需求 → 容量估算 → 架构 → 数据模型 → 安全 → 演进**。先问边界再动手（30 秒澄清 = 专业第一信号）；边画边讲（mermaid 习惯）。

**通用开场澄清三问**：①用户规模与并发 ②数据量级与更新频率 ③是否需要溯源/权限隔离。题干有明确数字就直接进容量估算。

**答案素材 = SCM Copilot 三域降维**：

| 面试题 | 映射域 | 复用弹药 |
|---|---|---|
| 设计企业知识库问答系统 | kb 域 | 混合检索（BM25+向量+RRF+重排）/ 语义缓存双闸门 / 引用溯源 + 反馈纠错回流评测集 / 夜间评测自动化 |
| 设计带数据分析的客服系统 | data + ops 域 | NL2SQL 四道闸 + 只读账号 + 行级权限注入（防越权）/ HITL 审批 / 自修复 ≤2 次 / 语义缓存 |
| 设计一个 Agent 平台底座 | platform 域 | 模块化单体 / RBAC / 审计 / 调度零重复 / 双实例无状态 / 故障演练降级链 |

**容量估算锚点（都有实测）**：Qdrant 432 QPS/P95 27ms（千万级以下单容器够）；300 万 chunk ≈ 1.5GB；混合检索 P95 27–300ms 级；40 并发 100% 成功 / P95 2.09s（单机+单连接串行根因）。

**安全纵深三段话术**：校验层（AST 确定性解析）→ 权限层（只读账号 ERROR 1142 兜底）→ 数据层（行级权限注入 WHERE tenant_id，防横向越权）。

**演进不硬撑**：数据量 100 倍 → 单库拆分（ADR-01 信号③）→ Qdrant 分片 → 计算密集域独立扩缩容；多租户增长 → 字段隔离 → 分片/分库分表。
