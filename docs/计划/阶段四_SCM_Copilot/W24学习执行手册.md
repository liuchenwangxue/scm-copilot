## 一、本周定位

W24 是 SCM Copilot 的**技术纵深主战场**：从零建出数据分析域（NL2SQL over MySQL），也是差距清单里面试价值最高的缺口（★★★）。

## 六、七天计划

### Day1（8/24 周一）★ 业务库与只读沙箱

**目标**：`scm_biz` 六表 + 万级真实感数据 + 只读账号，NL2SQL 的"靶场"今天就位。

**上午**：
1. `models_biz.py` 六表 ORM（DDL 见《02》3.2 节）：
   - `orders`（核心表，ENUM 状态 + `idx_status_created` `idx_region` 复合索引）
   - `order_items` / `products` / `suppliers` / `inventory` / `shipments`
   - 关系链：orders →(order_no)→ order_items →(product_id)→ products；orders →(supplier_id)→ suppliers
2. Alembic 建第二库：`alembic -x db=biz` 双迁移链（env.py 按 `-x` 参数选 DSN，platform/biz 两条 version 目录）
3. `deploy/initdb/01_create_ro_user.sql`：
   ```sql
   CREATE USER IF NOT EXISTS 'nl2sql_ro'@'%' IDENTIFIED BY '<random>';
   GRANT SELECT ON scm_biz.* TO 'nl2sql_ro'@'%';
   FLUSH PRIVILEGES;
   ```
   compose 的 mysql 挂 `./deploy/initdb:/docker-entrypoint-initdb.d`（仅首次初始化生效，改密码要重建容器）

**下午**：
4. `scripts/seed_biz.py` 固定 seed 生成器（`random.seed(42)`）：
   - 供应商 40：名称带区域词（华东/华北/华南/西南各 10）；评分 60–95
   - 商品 500：SKU 编码 + 类目 8 种 + 单价 10–5000
   - 订单 10,000：`SO-2026MMDD-XXXX` 编号；时间分布近 180 天（近 30 天加密 40%）；状态按 draft 5% / paid 20% / shipped 40% / done 30% / cancelled 5% 流转合法；金额与明细勾稽
   - 明细 30,000：每单 2–5 行；库存/发货表与订单状态一致（shipped 才有发货记录，延迟发货率 ~8% 供日报用）
5. 幂等验证：`make reseed-biz`（drop→create→seed）连跑两遍数据逐行一致（比对 COUNT + 3 表校验和）
6. 只读验证：用 nl2sql_ro 试 `UPDATE orders SET ...` → MySQL 拒绝（ERROR 1142）；`SELECT` 正常

**面试题 0.5h**：纵深防御叙事——为什么校验闸之外还要只读账号？（闸可能有未知绕过，权限层兜底；面试官追问"你敢让 LLM 生成的 SQL 直接跑吗"的满分答案）

**验收**：六表行数达标；重放一致；只读账号写被拒；Alembic biz 链可重放。
**坑**：
- ENUM 列的 ORM 写法 `Mapped[str]` + `_sa.Enum`，迁移脚本里核对 MySQL ENUM 而非 VARCHAR
- 种子的时间分布要刻意设计：评测里"近 7 天/近 30 天"类问题必须有数据可查（空结果集会被误判为 SQL 错）
- `docker-entrypoint-initdb.d` 只在数据卷为空时执行——重建用户要 `docker compose down -v`（会清掉平台库，小心顺序）

### Day2（8/25 周二）★ 安全四道闸

**目标**：`sql_validator.py` 四道闸 + 20 条攻击用例全拦——本周安全侧的"一夫当关"。

**上午**：
1. `sql_validator.py` 按权威实现落地（完整代码见《03》1.1 节）：
   - 闸1 `len(sqlglot.parse(sql, read="mysql")) == 1` 防堆叠
   - 闸2 根节点 `isinstance(tree, ALLOWED_ROOT)`（Select/Union/**含 UnionAll**）
   - 闸3 `tree.find(exp.Insert, exp.Update, exp.Delete, exp.Drop, exp.Alter, exp.Create, exp.Grant)` 子句级拦截
   - 闸4 `find_all(exp.Func)` 对 `sleep/benchmark/load_file/outfile` 黑名单
   - 兜底 `tree.limit(200)` 强制 LIMIT（无 limit 才加，别重复包一层）
   - 拒绝时 raise `SQLRejected(reason)`，reason 落审计
2. `executor.py` 沙箱执行器：
   - nl2sql_ro 连接池（独立 engine，与平台库隔离）
   - `asyncio.wait_for` 3s 超时；`LIMIT` 200 行数上限；结果集 >1MB 截断保护
   - 执行事件写 audit_logs（含被拒 SQL 原文，取证可回放）

**下午**：
3. `tests/test_sql_validator.py` 每闸至少 5 个单测分支：
   - 闸1：`SELECT 1; DROP TABLE orders;` / `SELECT 1; SELECT 2`
   - 闸2：`UPDATE ...` / `DELETE ...` / `INSERT ... SELECT`
   - 闸3：`SELECT (DELETE FROM orders)` / `SELECT * FROM orders WHERE id IN (UPDATE ...)` 伪装嵌写
   - 闸4：`SELECT sleep(5)` / `SELECT benchmark(1e7, MD5('x'))` / `LOAD_FILE('/etc/passwd')`
   - 混淆：大小写 `SlEeP` / 注释截断 `SELECT 1 -- ; DROP` / 编码 `\x73leep` / UNION 探测 `' UNION SELECT password FROM users--`
4. 20 条攻击用例固化为 `test_attack_cases.py` 参数化用例（pytest parametrize），要求 20/20 拒绝且 reason 正确
5. CI 接入：validator 单测 + 攻击用例进 pipeline

**面试题 0.5h**：Q3——四道闸分别防什么？只靠它够吗？（今天写完每条闸，答案已长在手上）

**验收**：攻击 20/20 拦截 0 逃逸；合法查询（含 join/聚合/子查询）0 误拦；超时/行数单测绿。
**坑**：
- `read="mysql"` 必传，否则 `LIMIT 200 OFFSET 10` 等方言解析漂移
- sqlglot 版本锁死（`sqlglot==25.x` 系），升级可能改 AST 结构——pin 在 pyproject
- 误拦检查别忘：`SELECT ... FOR UPDATE`（锁读）、`WITH cte AS (...)`（CTE 根节点是 `exp.Select` 包 `With`）——CTE 要放行，`FOR UPDATE` 拒绝

### Day3（8/26 周三）★ 生成链路 v1 与基线

**目标**：问题 → SQL → 闸 → 沙箱 → 表格 全链路第一次跑通，50 条基线有数字。

**上午**：
1. `prompts.py` v1 模板：
   ```
   你是 MySQL 专家。根据 schema 和问题生成单条 SELECT 语句。
   规则：只读；必须 LIMIT；时间列用 created_at；今日={today}。
   ## Schema（全六表 DDL + 中文注释）
   ## Few-shot（5 条：单表过滤/两表 join/聚合分组/时间窗/排序各一）
   ## 问题：{question}
   ```
2. `graph.py` NL2SQL 子图（LangGraph StateGraph，与 kb/ops 图同构复用组件）：
   - 节点：generate → validate →（reject→拒答）/（pass→execute）→（error→repair，W24-D5 补）/（ok→format）
3. `router.py` `POST /api/data/query`：JWT + `data:nl2sql` 权限 → 子图 → 返回 `{table, sql, columns, rows, elapsed}`

**下午**：
4. 评测集 v1（50 条，`seed(42)` 生成 + 人工审一遍问题措辞）：
   - 单表 30：过滤（区域/状态/时间窗）、排序 TOP N、去重计数
   - join 20：订单+明细金额汇总、订单+供应商按区域聚合、商品+库存低库存
   - 每条带标准结果（跑标注 SQL 的结果集快照，固定 seed 保证稳定）
5. `eval_nl2sql.py` execution accuracy 脚本：
   - 生成 SQL → 闸 → 执行 → 与标准**结果集**比对
   - 规范化：排序键统一（按第一列排序）+ 类型归一（Decimal→float、datetime→isoformat）+ 全 NULL 列对齐
   - 输出：总分 + 错例清单（问题/gold SQL/gen SQL/差异行）
6. mock 全链路验证 → **开 real 跑基线 50 条**（glm 免费额度）：记分层准确率 + P95 到 `nl2sql_baseline.md`

**面试题 0.5h**：Q4——为什么 execution accuracy 不做字符串比对？（同义 SQL 误判；今天评测脚本亲手实现，讲实现细节）

**验收**：单表 ≥0.90 基线（低于则当天排查 prompt/few-shot）；错例清单可复现。
**坑**：
- 日期边界：`近 7 天` 的口径写死在 few-shot（`created_at >= CURDATE() - INTERVAL 7 DAY`），否则模型各写各的
- `DECIMAL` 聚合返回 Decimal 类型，规范化漏了它 → 明明结果对却判错
- mock 模式测链路、real 测效果——两个数字分开记，别混在一张表里

### Day4（8/27 周四）★ Schema Linking

**目标**：全 schema 注入 → 相关表召回注入，token 砍半以上、精度不降反升。

**上午**：
1. `schema_linker.py`：
   - 语料：每表一条描述（表名 + 中文用途 + 关键列语义）；每列一条（`orders.amount` = 订单总金额，与明细行金额勾稽）
   - 复用 shared 的 bge-small embedding，问题向量 → 表/列召回 Top-3 表
   - 召回结果映射回完整 DDL 片段 + 对应 few-shot 优先注入
2. 召回评测集：50 条问题 → 人工标注"应包含的表"，算召回准确率（该在的表在 Top-3 里）

**下午**：
3. `prompts.py` v2：召回表 DDL + 精选 few-shot；v1/v2 用 `PROMPT_VERSION` 环境变量切换
4. A/B 跑 50 条基线：v1 vs v2 的准确率 + prompt token 消耗（mock 统计 token，real 抽 20 条对照）
5. join 类评测集补强至 40 条（本周评测集 90 条在途）；错例分析：错在表召回 or SQL 生成，分类计数

**面试题 0.5h**：schema linking 的价值不止省 token——相关表约束反而提高精度（"给的信息少而准"），讲 A/B 数字。

**验收**：召回准确率 ≥90%；token 下降 ≥50%；v2 准确率 ≥ v1（至少不降 2pp）。
**坑**：
- 表描述要写"勾稽关系"（订单金额=明细合计），否则 join 类问题模型瞎猜关联列
- 召回阈值别太松：Top-3 之外的表一律不进 prompt，宁可 linking 评测集里标注更多
- few-shot 与召回表联动：join few-shot 只在召回 ≥2 表时注入，否则干扰单表问题

### Day5（8/28 周五）★ 自修复与多轮

**目标**：报错能自救（≤2 次），追问能接住（"那华南呢？"）。

**上午**：
1. `repair.py` 错误自修复：
   - 捕获执行错误（ProgrammingError/OperationalError 的 message + errno）
   - 修复 prompt：原问题 + 原 SQL + 报错原文 → "仅修复语法/列名/表名错误，不改业务语义"
   - 循环 ≤2 次；修复后**仍过四道闸**（安全不豁免）；两次失败 → 降级话术："暂时无法生成有效查询，建议：{改写建议}"（把 gold 相似问题的改写方向给出来）——**不硬答**
2. 修复救回率评测：构造 30 条"故意坏 SQL"样本（错列名 10 / 错表名 10 / 语法错 10）过修复链

**下午**：
3. `session_ctx.py` 多轮追问：
   - 会话内保存上一轮 `{question, sql, tables}`；新问题做指代消解（LLM 一次调用：补全省份/时间/实体省略）
   - 例："上个月华东的延迟订单有多少" → "那华南呢？" = "上个月华南的延迟订单有多少"
   - 消解后的问题进生成链路（SQL 生成感知不到多轮）
4. 多轮评测 10 条（每条 2–3 轮），过 8 条达标
5. 回归：全量旧用例 + W23 认证用例仍绿

**面试题 0.5h**：降级设计哲学——"错误答案的代价远高于拒答"，讲 repair 的两次上限与降级话术设计。

**验收**：报错救回 ≥50%；多轮 10 条过 8；修复后的 SQL 100% 过闸；回归绿。
**坑**：
- 修复 prompt 必须强调"不改语义"——否则模型会把查不了的查询改成"能跑但答非所问"的 SQL（更危险）
- 指代消解单独一次 LLM 调用，别塞进 SQL 生成 prompt（两个关注点混在一起两头都差）
- 修复循环要记 trace（LangFuse 里能看到 generate→error→repair 的链路），面试演示素材

### Day6（8/29 周六）★ 呈现与全量评测

**目标**：本周成果收敛成"三个数字 + 一套呈现"，R1 检查点做决策。
