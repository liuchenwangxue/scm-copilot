## 一、本周定位

W23 是 SCM Copilot 的**地基周**：把 stage3-project-a（知识问答）和 stage3-project-b（业务操作）从"两个独立 SQLite 应用"重组为"一个 MySQL 权威库的模块化单体平台"。

本周不做任何新业务功能，只做三件事：

1. **身份统一**：JWT 登录对接 MySQL 用户-角色-权限三级模型（替换 W21 的配置式白名单）
2. **双域复活**：两项目代码迁入统一应用，路由/中间件/组件三统一，旧 109 项回归保持全绿
3. **状态外置**：审批/审计/反馈/checkpointer 全部从 SQLite/进程内迁到 MySQL+Redis，最后用 least_conn 双实例验证"真无状态"

> 一句话目标：**周五结束时有"一个能登录的平台骨架"，周六压测证明"任意实例可杀、数据零丢失"。**

成就感公式：**周一建仓见 CI 绿、周二五表可迁移、周三登录进平台、周四双域全回归、周五数据搬家零误差、周六双实例杀不死的平台、周日复盘定 W24。**

### Day1（8/17 周一）★ 建仓与 MySQL 接入

**目标**：仓库骨架 + MySQL 容器 + CI 三件套今天就位，明天一起床就能建模。

**上午（核心 3h）**：

2. 从 `stage3-project-a` 复制工具链四件：`pyproject.toml` 的 `[tool.ruff] [tool.mypy] [tool.pytest.ini_options] [tool.coverage]` 段落，改包名为 `backend.app`
3. 写 `deploy/docker-compose.yml` MySQL 8 单服务：
   ```yaml
   services:
     mysql:
       image: mysql:8.0
       environment:
         MYSQL_ROOT_PASSWORD: root123
         MYSQL_DATABASE: scm_platform

       healthcheck:
         test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
         interval: 5s
         retries: 10
   volumes: { mysql_data: {} }
   ```
4. `app/main.py` 最小骨架：lifespan 里建 async engine + `GET /health` 返回 db 连通状态

**下午（3.5h）**：
5. GitHub 建仓 `scm-copilot` + push；`.github/workflows/ci.yml` 从 stage3-a 复制，改路径为 `backend/`，job 步骤 ruff → mypy → pytest → coverage
6. CI 里 MySQL service container（`services: mysql: image: mysql:8.0` + health cmd），跑一个连通性测试用例
7. Makefile：`up`（compose up -d）/ `down` / `migrate`（alembic upgrade head，明天补）/ `test`

**面试题 0.5h（20:00 段）**：ADR-02——为什么权威库选 MySQL 8 而不是继续 SQLite / 上 PostgreSQL？（答题要点见《04》：并发写行锁、双实例单写者锁不可行、运维熟悉度）

**验收**：`docker compose up -d mysql` 后 `docker ps` 显示 healthy；容器内 `SELECT NOW()` 时间为北京时间；push 后 CI 全绿。
**坑**：
- Windows + WSL2 下数据卷用**命名卷**不用绑定挂载（`./data:/var/lib/mysql` 会因 NTFS 权限使 InnoDB 初始化失败）
- `TZ` 必须设，否则所有 `DATETIME(3)` 默认值差 8 小时——W24 评测里"近 7 天"类查询会全错
- CI 的 MySQL service 起在 job 容器里，host 名就是 service 名 `mysql`，不是 localhost

### Day2（8/18 周二）★ 平台库建模

**目标**：五表三级权限模型 + 伴随表全部落 Alembic 版本化，seed 可重放。

**上午**：
1. `alembic init -t async`（async 模板），`env.py` 接 settings 的 `PLATFORM_DSN`
2. `platform/models.py` 按顺序写 ORM（DDL 完整版见《02》3.1 节）：
   - `users`：`password_hash VARCHAR(97)` 精确对应 bcrypt 输出长度；`tenant_id` 多租户隔离键（W24 行级数据权限用）
   - `roles`：code 唯一（admin/operator/analyst/viewer）
   - `permissions`：code 形如 `kb:chat` / `ops:order:update` / `data:nl2sql` / `admin:user:manage`，domain 字段按域分组
   - `role_permissions` / `user_roles`：复合主键关联表
3. 伴随表：`audit_logs`（event/actor/trace_id/created_at + 索引 actor,created_at）/ `approvals`（含 `diff_before` `diff_after` JSON）/ `feedback` / `api_keys` + `quota_usage`（本周只建表不实现）/ `scheduler_job_runs`（W25 用）/ `conversations`
4. `alembic revision --autogenerate -m "platform core tables"` → 人工 review 生成脚本（ENUM/索引/字符集）

**下午**：
5. `scripts/seed_platform.py` 幂等种子：
   - 4 角色固定 id 1–4；权限码 12 条（kb 3 + ops 4 + data 2 + admin 3）
   - 角色-权限映射：admin 全量 / operator（kb+ops）/ analyst（kb+data）/ viewer（kb 只读）
   - 3 租户 × 4 角色测试用户，密码 bcrypt（明文 `Passw0rd!`，写进 README 开发文档）
   - 幂等实现：`INSERT ... ON DUPLICATE KEY UPDATE` 或先查后插
6. 验证轮：`alembic downgrade base && alembic upgrade head && python scripts/seed_platform.py` 连跑两遍无报错
7. 补 CI：migrate + seed 步骤加进 workflow（保证 PR 合并前 schema 一定合法）

**面试题 0.5h**：RBAC 三级模型（用户-角色-权限）对比 W21 配置式白名单的收益——权限可运营（管理员界面增删）、可审计（权限变更本身落 audit_logs）、多租户可扩展。

**验收**：`upgrade head` 从零可重放；downgrade→upgrade 一轮通过；seed 跑两遍结果一致；CI 绿。
**坑**：
- SQLAlchemy 2.0 写法：`Mapped[int]` + `mapped_column()`，别用 1.4 的 `Column()` 老写法（mypy 插件认不出类型）
- bcrypt 有 72 字节输入上限，密码超长先 hash 会 silent truncate——登录校验前限制长度
- Alembic autogenerate 识别不了表注释和 ENUM 变更，这类改动手写进迁移脚本

### Day3（8/19 周三）★ 认证链路

**目标**：登录走 MySQL、权限走依赖注入、写操作全审计——平台"有门禁了"。

**上午**：
1. `platform/auth.py` 三个端点（从 W21 实现改造，核心差异：用户来自 DB）：
   - `POST /api/auth/login`：username+password → bcrypt 校验（`secrets.compare_digest` 防时序）→ 签 15min access + 24h refresh → 登录事件写 `audit_logs`
   - `POST /api/auth/refresh`：refresh 换新 access（rotation：旧 refresh 作废）
   - `POST /api/auth/logout`：JWT 无状态 → 登出走"吊销名单"（Redis `jti` 黑名单到 access 过期；本周可先落库版）
2. `platform/rbac.py` 依赖注入工厂（复用 W21 的 `require_roles` 闭包模式，升级为 `require_permission("ops:order:update")`——查 user_roles → role_permissions 链）
3. `platform/audit.py` ASGI 中间件：非 GET 请求 → 落 `audit_logs`（event=method+path / actor=sub / trace_id / status）

**下午**：
4. `/health` `/docs` `/metrics` 三端点放行（白名单常量），其余路由挂全局 JWT 依赖
5. `tests/test_auth.py` 三态用例（对照 W21 的 17 条改造）：
   - 401：无 token / 过期 token / 篡改签名 / 错账号密码
   - 403：viewer 调 admin 端点 / analyst 调 ops 写操作 / 跨租户访问
   - 200：四角色各自合法路径
6. `tests/test_rbac.py` 权限矩阵：4 角色 × 12 权限码 = 48 格全断言（正交覆盖，防"漏配权限"）

**面试题 0.5h**：401 vs 403 的语义边界（未认证 vs 已认证无权限）+ JWT 双令牌为什么 access 短 refresh 长（泄露窗口 vs 体验）。

**验收**：curl 登录拿 token → 带 token 200 / 不带 401 / viewer 访问 admin 403；audit_logs 有记录；三态+矩阵用例全绿。
**坑**：
- JWT 的 `sub` 放 user_id（不是 username），`tenant_id` `roles` 进 claims，权限判定才不用每请求查库
- bcrypt 慢（~100ms）是特性不是 bug（防爆破），登录接口别套慢日志告警
- 中间件顺序：审计在 JWT 之后（audit 的 actor 需要 claims 里的 sub）

### Day5（8/21 周五）★ 数据迁移与 checkpointer

**目标**：历史数据（审批/反馈/审计）无损搬进 MySQL，LangGraph 断点换库后还能续跑。

**上午**：
1. `scripts/migrate_sqlite_to_mysql.py`（方案见《03》第 5 节）：
   - 读 stage3-b `biz_agent.db` 三类表 → 映射写 `scm_platform.approvals / feedback / audit_logs`
   - 幂等：按业务主键（审批单号/反馈 id）`INSERT ... ON DUPLICATE KEY UPDATE`
   - 校验和：逐表 `COUNT(*)` + 每表取 3 个关键字段做 `md5(concat(...))` 聚合比对
2. LangGraph checkpointer：SQLite saver → `AsyncMySQLSaver`（`langgraph-checkpoint-mysql` 包，注意装平台库 DSN）
3. 会话历史表 `conversations` 写入路径接通（kb 域的 session 持久化改 MySQL）

**下午**：
4. HITL 断点迁移验证（复用 W2 演练场景）：
   - 发起高危操作 → 审批中断 → **杀进程重启** → 审批通过 → 图从断点 resume 继续执行
   - 老会话验证：迁移前的 thread_id 在新库继续追问（checkpointer 历史迁移或声明"新会话开始"，如实记录）
5. 语义缓存 keys 迁 Redis（stage3-a 进程内字典/单实例 db）→ `scm:semcache:*` 共享前缀
6. 跑全量回归 + 把 Day3/Day4 用例并进 CI

**面试题 0.5h**：数据迁移怎么保证不丢不错？（行数比对只是入门，关键字段校验和 + 幂等可重跑 + 迁移前后双写窗口——答出层次感）

**验收**：迁移脚本输出"3 表行数一致 + 9 组校验和一致"；HITL 杀进程续跑成功；回归全绿。
**坑**：
- SQLite 的 `DATETIME` 是 TEXT，迁移时显式 `STR_TO_DATE` 转格式，别信隐式转换
- `AsyncMySQLSaver` 需要在 lifespan 里 `setup()` 建表，别在 import 时连库
- 语义缓存 keys 迁完务必双实例验证命中（一个实例写入另一个能看到），否则 W24 会误判"缓存失效 bug"

2. compose 扩容：`backend-a1` `backend-a2`（同镜像不同容器名）+ `nginx` 服务；`nginx.conf`：
   ```nginx
   upstream backend { least_conn; server backend-a1:8795; server backend-a2:8795; }
   server {
     listen 80;
     location / { proxy_pass http://backend; proxy_buffering off; proxy_read_timeout 300s; }
   }
   ```
   （`proxy_buffering off` 保 SSE 流式，W20 教训）
