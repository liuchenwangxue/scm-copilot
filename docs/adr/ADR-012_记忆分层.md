- 相关：`00_问题总清单` D3（记忆分层）、hello-agents ch8、W23 feedback 表

## 一、背景与问题

项目现状的"记忆"散落在四件套里，但**没有分层模型**，且长期记忆的原材料
（feedback 表）**从 W23 建表至今未回流**——数据在积累，管道未接通：

| 记忆类型 | 现状载体 | 语义 | 状态 |
|---|---|---|---|
| 工作记忆 | MySQL checkpoint（ops 域） | 单次任务的消息 + HITL 现场（审批断点） | ✅ 已用 |
| 短期记忆 | Redis session_ctx（data 域轮次，W27-D2 外置） | 多轮会话"上一轮上下文"（question/sql/tables） | ✅ 已用 |
| 会话元数据 | conversations 表（MySQL） | 会话归属/标题/时间线 | ✅ 已用 |
| **长期记忆原材料** | **feedback 表（W23 建）** | 用户 like/dislike/correction + 查询历史 | ⚠️ **未回流** |

D3 诉求：按 hello-agents ch8 的分层模型（工作/短期/长期）把四件套对齐，
并给出"长期记忆回流管道"设计——**代码留三期，本日只成文**。

## 二、设计：四件套分层 + 回流管道

### 2.1 分层映射（现状 → 目标）

```text
┌─────────────────────── 记忆分层（W28-D6 设计） ───────────────────────┐
│                                                                        │
│  工作记忆    MySQL checkpoint (ops)        单任务现场/HITL 断点          │
│     ↓ 任务结束收敛                                                        │
│  短期记忆    Redis session_ctx (data)     多轮轮次上下文（≤max_turns）   │
│     ↓ 会话归档                                                           │
│  会话元数据  conversations 表 (MySQL)      归属/标题/时间线              │
│                                                                        │
│  长期记忆原材料 feedback 表 (MySQL/jsonl)   correction + 查询历史         │
│     ↓ ★ 夜间 job 挖掘（三期第一项）                                      │
│  用户偏好表  user_preferences (MySQL)      {user, domain, pattern, w}    │
│     ↓ 注入                                                               │
│  kb/data prompt 个性化上下文                "该用户偏好华东/近30天口径"   │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.2 回流管道（设计，代码留三期）

```text
反馈/查询历史(feedback 表)
  → 夜间 job `feedback_mining`（挂 scheduler，同 eval_nightly 纪律）
      筛选 status=approved 且 action=correction 的记录
      解析 correction：提取 {domain(region/time/status), value, weight}
      + 查询历史统计：该用户高频使用的 region/time 口径
  → user_preferences 表（MySQL，新表 + alembic 迁移）
      {user_id, domain, value, weight, updated_at}  唯一键 (user_id, domain, value)
  → 注入点（三期接入，先空跑统计）：
      kb 检索 query 改写：该用户常问华东 → 检索时 region 权重提升
      data prompt：该用户偏好近30天/华东 → 消解 prompt 附偏好提示
```

### 2.3 防污染与隐私纪律（延续既有原则）

- **只回流 approved correction**（like/dislike 是信号不是事实，只进统计不进偏好）；
- 去敏：user_id 只留角色/编号，不存个人可识别信息（与 feedback 表一致）；
- 注入是"提示级"不是"数据级"：偏好只影响检索权重/消解提示，不改最终事实——
  结果仍必须来自真实数据（沿用 insight.py"禁止编造数字"双保险）；
- 可回退：`SCM_MEMORY_MINING=off`（默认关）→ 管道不跑，行为与现状完全一致。

## 三、面试叙事（为什么这是完整答案）

1. "数据已在积累"：四件套 + feedback 表证据（W23 建表至今）——不是从零开始；
2. "管道设计好了"：夜间 job 挖掘 → 偏好表 → 注入点，三层闭环（本 ADR）；
3. "代码为什么留三期"：记忆回流是"锦上添花"而非"地基"——优先级低于面试
   高频考点（MCP/性能/覆盖率），明确 ROI 排序后主动排期，体现工程取舍。

## 四、未做/边界（诚实记录）

- 无代码落地（三期第一项）：本 ADR 只交付分层模型 + 管道设计 + 表结构草案；
- 无 A/B 验证设计：偏好注入对检索质量的影响需三期用既有评测集跑 Δ
  （同 feedback 回流评测集的先例）；
- 无跨域统一记忆 API：kb/data 各自注入点独立，不引入"全局记忆服务"
  （避免过度设计；若三期两域都接入再抽公共层）。
