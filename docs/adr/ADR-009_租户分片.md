# ADR-009：租户隔离从 payload 过滤演进到 collection 分片

- 状态：已采纳（W28 Day4 落地，C4/B7）
- 日期：2026-09-03（W28-D4）
- 相关：ADR-010（读写分离，同日入库）、`docs/计划/阶段五_SCM_Copilot二期改进/00_问题总清单.md` C4/C5
- 影响代码：`backend/app/shared/rag/sharding.py`（路由）、`domains/kb/tenant/tenant_filter.py`（双保险封装）、`shared/rag/store.py`（collection 覆盖）、`shared/rag/hybrid_retriever.py`（BM25 租户过滤）

---

## 一、背景与问题

W18 起租户隔离采用 **payload 过滤级**：单 collection `scm_kb_v1`，所有检索强制 `must tenant_id`。
这套方案在文档体量小（2543 块）、租户少（3 个演示租户）时正确且零额外成本，但存在两个规模化瓶颈：

1. **性能**：所有租户共享一个 HNSW 索引——租户数与点数增长后，单次检索的全库扫描与候选集
   召回随总点数线性恶化，一个租户的写入（增量同步）也影响所有租户的检索延迟（写放大共享）。
2. **C5 漏洞（同日排查补齐）**：BM25 路此前没有租户维度——`BM25Index` 的 chunk 元数据无
   `tenant_id`，`search()` 全量打分返回，混合检索的 BM25 候选可能跨租户泄露（payload 过滤
   只管向量路，管不到 BM25 路）。

**决策目标**：租户隔离从"正确性"走向"规模化有路"——分片是性能隔离，payload 过滤作为
正确性兜底保留（双保险）；同时把 BM25 路漏洞堵上，双路（向量+BM25）租户不可见。

## 二、决策：三级演进，本步到第二级

租户隔离按数据规模分三级演进，**触发条件达到才升一级**（不为演示规模做生产级基建）：

| 级别 | 方案 | 检索特征 | 迁移成本 | 触发条件（量化阈值） |
|---|---|---|---|---|
| L1 | payload 过滤（单 collection） | 全库共享索引，Filter 强制 tenant_id | 零 | 默认（当前基线） |
| **L2** | **collection 分片（本 ADR 采纳）** | 租户 → crc32 路由到独立 collection，分片内 HNSW 更小 | 中（一次性迁移脚本，可灰度） | 租户数 > 12 **或** 单 collection 点数 > 10 万 且 P95 检索超预算 |
| L3 | 独立实例（每租户专用 Qdrant/索引） | 物理隔离最强、故障域独立 | 高 | 单租户检索 P95 仍超线（说明分片内 HNSW 也到上限）或合规要求物理隔离 |

> 阈值依据：Qdrant HNSW 在 10 万点内 `ef=200` 召回率与延迟曲线平缓；本项目单 collection
> 数千点远未到线——所以分片的价值主要在"演示规模化路径 + 性能隔离实证"，而非当前容量刚需。

## 三、L2 实现（本项目落地）

### 3.1 路由层（`shared/rag/sharding.py`）

```python
SHARDING_ENABLED = config.SCM_SHARDING in ("1", "on", "true", "yes")   # SCM_SHARDING=off 默认
SHARD_COUNT = config.SHARD_COUNT                                        # SCM_SHARD_COUNT=4

def collection_for(tenant_id: str, shards: int | None = None) -> str:
    if not SHARDING_ENABLED:
        return base_collection()                    # 灰度开关：off = 行为不变
    return f"{base_collection()}_{zlib.crc32(tenant_id.encode()) % shards}"  # scm_kb_v1_0..3
```

- crc32 确定性路由：同租户永远同分片 → 迁移脚本幂等可重跑（point id 保持 uuid5(text) 内容寻址）。
- 已知坑：crc32 对**少量租户分布会倾斜**（4 分片 × 3 租户可能 2/1/0/0）。处理：演示数据补足
  12 租户验证分布铺满（`sharding.distribution()` 有测试断言），倾斜本身在"分片数 > 租户数"
  场景下无性能危害（空分片零成本），ADR 记录并接受。

### 3.2 检索层双保险（`tenant_filter.py` + 检索器）

- `Retriever/HybridRetriever.retrieve(..., tenant_id=None)`：`tenant_id` 非空时——向量路先
  `collection_for(tenant_id)` 路由分片 **且** 注入 payload filter（`SCMStore.query(collection=..., tenant_id=...)`）；
  `tenant_id` 为空 = 公共语料检索，行为与分片前完全一致（调用方无感知）。
- **双保险语义**：分片是性能隔离；payload filter 是正确性兜底——即使路由层被绕过
  （把 A 租户 filter 拿去查 B 分片），检索结果必为空（验证脚本 `verify_sharding.py` 有
  "路由绕过模拟"实证）。
- BM25 路（堵 C5）：`BM25Index` 构建/加载时解析 chunk 的 `tenant_id`（缺失 = None = 公共语料）；
  `search(query, top_k, tenant_id)` 先按租户过滤出候选集再打分排序（rank_bm25 分数逐文档独立，
  全量打分 + 候选集排序与子集重建等价）；未知租户 → 空（fail-safe，宁缺毋滥）。

### 3.3 迁移与灰度

- `scripts/migrate_sharding.py`：base collection scroll 全量 → 按租户（payload 有则用之，
  `--tenant-policy spread --tenants 12` 可造演示分布）哈希路由 → 幂等 upsert 到分片
  （point id 原样保留，重跑覆盖零重复）；`--dry-run` 只出分布表。
- **灰度**：迁移期间新旧并存，`SCM_SHARDING=on/off` 运行时切换、回退零成本。
- 分片 collection 的 HNSW 参数（m/ef_construct）与 base 一致——否则分片间召回率不齐（坑记录）。

## 四、影响与成本

| 维度 | 说明 |
|---|---|
| 性能 | 分片内语料更小 → 检索更快（验证脚本并发对比实证）；写放大隔离到单分片 |
| 正确性 | 双保险：payload 过滤不删，路由是加分项不是替代 |
| 迁移 | 一次性脚本（幂等）；灰度开关零回退成本 |
| 运维 | 分片 collection 数 = 分片数（固定 4），非租户数——可控 |
| 存储 | 分片间向量有副本（迁移是复制非搬移，源保留供灰度）；可后续清理 |

## 五、未做/边界（诚实记录）

- L3 独立实例：仅留演进路径，未实现——当前规模不需要，且合规未要求物理隔离。
- 写入路径分片：增量同步（`kb_increment_sync`）当前写 base 公共 collection；租户专属语料由
  带 `tenant_id` 的写入脚本/接口负责（验证脚本演示）。"同步任务按租户写各自分片"列三期 backlog。
- crc32 倾斜：接受并记录（见 3.1），不引入一致性哈希（当前租户数远小于分片数）。

## 六、验证与证据

- 单测：`test_sharding.py`（路由确定性/分布/开关灰度）、`test_bm25_tenant.py`（BM25 双租户
  零交集/缓存加载保留租户维度/透传）、`test_tenant_filter_sharded.py`（双路判定/off 退化）。
- 实测脚本：`scripts/migrate_sharding.py --dry-run`（分布证据）+
  `scripts/verify_sharding.py`（路由隔离/绕过兜底/并发性能/删除隔离三件套）。
- 回归：KB 域全量测试绿（TenantFilter 接口不变，路由对调用方透明）；全量测试绿。

## 七、回退方案

`SCM_SHARDING=off` → 检索走 base collection，payload 过滤级语义原样恢复；
迁移脚本幂等，重跑零副作用；无数据破坏性操作（迁移只 upsert 不删除）。
