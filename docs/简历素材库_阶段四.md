## 一、SCM Copilot 项目 STAR（W23 平台地基段）

### 主线 1 · 平台化整合（本阶段总叙事，W23 已实证）

```
S 情境：两个独立 Agent 应用（stage3-a 知识问答 / stage3-b 业务操作）各自 SQLite 单实例，
        账号体系割裂、状态进程内、无法水平扩展——"上线容易运营难"。

T 任务：整合为模块化单体生产平台，实现统一账号/审计/调度/监控/开放 SDK，
        双实例无状态水平扩展；本周先打地基（身份统一 + 双域并入 + 状态外置）。

A 行动：
  ① MySQL 8 权威库：平台库 12 表（Alembic 版本化，从零可重放），RBAC 三级模型落库
  ② JWT 双令牌（15min access + 24h refresh + rotation）+ 全局门禁 + 写操作全审计
  ③ stage3 双项目迁入统一应用：共享层去重（llm/rag/reliability/obs 合并），认证审计统一
  ④ 状态全外置核销：checkpointer/审批/会话 → MySQL，幂等/缓存/锁 → Redis
  ⑤ least_conn 双实例 + nginx proxy_next_upstream + 压测/杀实例演练

R 结果（全部实测）：
  - 68 项回归全绿（原 109 项按同语义合并折算）；ruff/mypy 0 error
  - 双实例 30 并发正式：210/210=100%，P95 1275ms（≤1.5s 达标）
  - 40 并发极限：200/200=100%，P95 1823ms（按 R5 如实记录，根因=ops checkpointer 单连接）
  - 压测中杀 backend-a1：5xx=0，210/210 成功；重启容器数据零丢失
  - 迁移 4 类数据校验和全一致（feedback 13 / audit 19 / checkpoints 358 断点 + 858 写入）
```

### 主线 2 · NL2SQL 安全与准确（W24 已实证）

```
S 情境：平台要能"用自然语言查业务库"——既要查得准（生成 SQL 语义正确），
        又要防得住（注入/越权/拖库），而 LLM 生成的 SQL 天生不可全信。

T 任务：从零建 NL2SQL 数据分析域：业务库六表万级种子 + sqlglot 四道闸 +
        只读沙箱 + Schema Linking + 错误自修复 + 结果洞察，配 100 条三层评测集。

A 行动：
  ① scm_biz 六表（orders 1 万 / 明细 3.5 万）固定 seed 可重放 + nl2sql_ro 只读账号
  ② sqlglot AST 四道闸（单语句/仅SELECT/禁写/危险函数 + FOR UPDATE/表白名单扩展），
     强制 LIMIT 200；配 20 条攻击用例固化
  ③ 生成链路：问题→Schema Linking（bge 表列召回 Top-3 注入）→LLM→四道闸→只读沙箱
     →表格+SQL 透出+洞察摘要；错误自修复 ≤2 次 + 降级话术（不硬答）
  ④ execution accuracy 评测（结果集比对非字符串比对）：类型归一 + 列子集/同义别名对齐

R 结果（全部实测，kimi-k2.7-code real 100 条）：
  - execution accuracy 整体 0.970（单表 0.975 / join 0.950 / 聚合 1.000）
  - Schema Linking 召回 1.000；prompt token 降 53.5% 且精度反升（v2 1.000 ≥ v1 0.980）
  - 攻击 20/20 拦截 0 逃逸；只读账号 ERROR 1142 兜底；P95 38.9ms
  - 错误自修复救回 0.933（28/30）；多轮追问 9/10；洞察数字溯源双保险抽查全 PASS
```

### 项目一句话（简历项目标题下）

> 供应链智能运营平台（SCM Copilot）：整合知识问答（RAG）与业务操作（审批/幂等/熔断）双域，

> 双实例 least_conn 无状态水平扩展——压测 210/210 成功率 100%、P95 1275ms、
> 压测中杀任意实例 5xx=0 服务不中断、容器重启数据零丢失。

### 追问话术（防"背稿感"）

- "为什么选 MySQL 8 而不是继续 SQLite？"（ADR-02）→ "SQLite 单写者锁在双实例下不可行，行锁+并发写在运营数据上是刚需；SQLite 保留为 Redis 故障 fail-open 降级"
- "ip_hash 换 least_conn 的前提？"（《05》Q2）→ "状态全外置核销清单逐项打勾（见下）；粘滞路由存在的唯一理由是实例内存有状态，状态外置后 ip_hash 反而负载不均"
- "旧 109 项回归为什么变 68 项？" → "同语义合并 + 平台基座接管认证/审计（原两套 JWT/RBAC/审计各删一套），Day4 报告记录逐条合并明细"
- "迁移数据怎么保证不丢不错？" → "行数比对只是入门：COUNT + 关键字段 md5 校验和 + 幂等可重跑（连跑 3 遍）+ 存在性校验；空源如实记录（approvals 0 行不造假）"
- "40 并发 P95 为什么没到 1.5s？" → "ops checkpointer 单连接串行是根因（断点在 MySQL 权威库 vs 高并发的权衡，真实 ops 低频可接受）；按 R5 降 30 并发正式达标——不造假指标"
- "双实例为什么不用 ip_hash？" → "见 least_conn 前提；同时 nginx proxy_next_upstream 让杀实例时新请求零失败（error/http_502/http_503 自动切健康实例）"

## 四、W23 面试弹药（对接《05》）

| 面试题 | W23 弹药 |
|---|---|
| Q1 模块化单体 vs 微服务 | 域间强关联 + 单机约束；模块按 API 边界隔离（kb/ops/data），负载/团队/写瓶颈信号出现才拆 |
| Q2 ip_hash→least_conn 前提 | 状态全外置核销清单 8 项逐项打勾（JWT/会话/断点/审批/幂等/缓存/锁/调度） |
| 数据迁移方法论 | COUNT + 校验和 + 幂等可重跑 + 存在性校验；空源如实记录；HITL 断点跨库续跑实证 |
| 认证审计设计 | JWT sub=user_id + tenant_id/roles 进 claims（权限零查库）；审计在 JWT 之后（actor 来自 claims）；写操作审计 100% |
| 无状态化 | checkpointer=AsyncMySaver（collation 1267 坑）、语义缓存 Redis 共享双实例命中验证、幂等 SETNX fail-open |
| 排障顺序 | 先关"观测的同步 IO"→ 再看"连接池与刷盘"→ 最后业务层；异步化若破坏时序契约果断回退 |

### W24 面试弹药（NL2SQL，Day7 追加）

| 面试题 | W24 弹药 |
|---|---|
| Q3 sqlglot 四道闸分别防什么？只靠它够吗？ | 闸1 单语句防堆叠 / 闸2 仅 SELECT 根节点 / 闸3 子句级禁写防伪装嵌写 / 闸4 危险函数黑名单 + FOR UPDATE/表白名单扩展；**不够**——配 nl2sql_ro 只读账号（ERROR 1142）+ 3s 超时 + 行数上限，纵深防御即使有未知绕过权限层兜底 |
| Q4 为什么用 execution accuracy 非字符串比对？ | 同义 SQL 大量存在（LEFT JOIN vs 子查询/列序/别名），字符串比对大量误判；评测目标是"答对数据"。实现：结果集类型归一（Decimal→float、datetime→isoformat）+ 排序键整行 + 列子集/同义别名对齐 |
| LLM 生成的 SQL 你敢直接执行吗？ | 不敢——两层：AST 白名单（确定性、默认拒绝只放行查询）+ DB 最小权限（即使漏了也写不进）；追问"你敢让模型直接跑"的满分答案 |
| Schema Linking 只是省 token 吗？ | 实测 token 降 53.5% **且精度反升**（v1 0.980→v2 1.000）——"信息少而准"约束模型不乱挑表；错例可归因（表召回 vs SQL 生成分开计数）；可扩展到百表场景 |
| 错误自修复怎么防止"修出更危险的 SQL"？ | 修复 prompt 强约束"不改语义"+ 修复后**强制重新过四道闸**（安全不豁免）；安全类闸拒永不修复；≤2 次失败即降级话术（不硬答）——错误答案代价远高于拒答 |
| 洞察摘要怎么防止编造数字？ | prompt 给结果集 JSON（前 10 行）+ **确定性数字溯源校验**双保险：摘要中每个数字必须能在结果集数值单元格找到（% /万/千/亿 量纲换算 + 1% 容差），查无出处的整条丢弃 |

### W25 面试弹药（调度 + 开放能力，Day7 追加）

| 面试题 | W25 弹药 |
|---|---|
| APScheduler 多实例怎么防重复执行？ | 三层：① 调度器全实例跑（高可用，任一台挂了别的照常触发）② leader 锁 SETNX NX EX + owner 校验 Lua 释放（互斥执行，未抢到记 skipped 可观测）③ 任务幂等键（uuid5 内容寻址 / 日期键 SETNX，锁失效时副作用为零）——高可用 / 互斥 / 一致性三问题分治 |
| KB 增量同步的幂等设计？ | uuid5 内容寻址（同文本同 point id，重复同步=覆盖写）+ last_sync_ts 水位（成功才推进、取扫描开始时刻防漏检）+ payload 过滤删向量（增量拿不到 point id） |
| 日报数字怎么保证可回溯？ | 三条 NL2SQL 走生产四道闸 + 只读沙箱真实执行，SQL 原文随 brief 落库——每个数字点开就是 SQL，不 hand-fill |
| SDK 为什么手写不生成？（ADR-08） | 三接口手写换可控性（SSE 迭代器体验 / ScmQuotaError 领域化异常 / httpx 单依赖），OpenAPI 契约已就绪是演进路径——接口少手写换可控，接口多生成换生产力 |
| 白天聊 key 哈希用 sha256 不用 bcrypt？ | 校验是每请求高频路径，bcrypt 100ms 不可接受；API Key 128bit 熵防猜测靠熵而非慢哈希——密码 bcrypt（低频 + 撞库防护）与 Key sha256（高频 + 熵防护）策略分开 |
| Hooks 机制怎么落地？（s04 映射） | PreToolUse（参数校验 + 审计埋点）挂工具执行前、PostToolUse（结果审计 + 缓存失效）挂执行后——审计/校验/失效三个横切关注点全部挂钩子，execute_node 本体一行不膨胀；钩子抛错 try/except 放行（横切故障不拖垮主链路，ADR 修订-1） |
